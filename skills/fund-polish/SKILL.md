# /fund-polish — 基金申请书润色与格式终检

## 触发场景
基金申请书内容基本定稿，需要进行语言润色、说服力强化和格式合规检查。

## 工作流

### Step 0: 阶段入场（reviewed → polishing）

开始时若项目阶段为 `reviewed`，更新 CLAUDE.md 的 `## 项目阶段` 为 `polishing`。

> 单一责任方：`reviewed → polishing` 的转换由本 skill（/fund-polish）负责；上游 /fund-review 只负责 `drafting → reviewed`，不越位。

### Step 1: 读取申请书全文

- 如存在 `reviews/fund_review_report_*.md`（由 /fund-review 生成），读取最新评审报告，针对评审指出的问题重点润色。
- 从 `sections/` 目录读取各章节 md 文件。
- 确认基金类型和目标基金的格式要求
- 如有格式模板/填写说明，一并读取

### Step 2: 语言润色（调用 `language-polisher-zh` agent）

#### 2.0 Agent 调用协议（Mode A：Pipeline）

**逐章**调用 `~/.claude/agents/language-polisher-zh.md`（镜像 /diss-polish Step 5 的结构；不要 ad-hoc 调用，否则写作 brief/基金语境丢失）：

```
subagent_type: general-purpose
model: opus
（不传 isolation 参数——全局红线）

prompt：
你是中文学术论文润色专家（language-polisher-zh）。Mode A: Pipeline invocation from /fund-polish.

## 输入
- 目标文件：{sections/{章节编号}_{章节名}.md}（完整读取）
- 写作 brief：本项目为中文基金申请书（{国自然/省基金/校级}），非论文/非学位论文
- 评审报告：{reviews/fund_review_report_最新.md}（若存在，作为内容层修复方向）
- 项目术语表：{从 CLAUDE.md 提取，若存在}
- 字数上限：{从 CLAUDE.md `## 章节规划` 本章"目标字数"列的**上界**（如 "2000-3000" 取 3000），润色时字数不得超过此值}

## 任务
按以下 5 个维度润色本章全文（见 2.1-2.5 详述），并附加**基金专属约束**：
- 说服力强化：每段回答"为什么值得资助"；禁止描述性陈述
- 评审视角：目标读者是见过数百份申请书的资深评审专家
- 时态约束：未完成工作用将来时，已有成果用过去时
- AIGC 规避：避免过度连词/模板句式/空洞论断

## 输出
- 润色后的完整章节文本
- 修改摘要：按"原文 → 润色后 → 修改理由"三列表格呈现（用于 Step 4 展示）
- AIGC 自检清单：主动检查过度连词、模板句式
```

**约束**：
- 一次一章，不并行（基金正文章节间逻辑耦合紧，需用户章间确认才推下一节）
- 读取 Agent 的输出后**不立即写回文件**——进入 Step 3 自审

#### 2.1 学术规范性
- 表述是否符合基金申请书的文体要求（不同于论文、不同于报告）
- 是否存在口语化表达、冗余表述、语病
- 被动句/主动句使用是否恰当
- 避免过度自谦或过度夸大

#### 2.2 说服力强化
- **立项依据**：是否构建了清晰的"已知→未知→本项目填补"逻辑链？
- **研究意义**：是否同时覆盖理论意义和实践价值？是否有具体场景/数据支撑？
- **创新点**：表述是否锐利、不含糊？是否避免了"一定程度上""有所创新"等弱化词？
- **研究方案**：是否给评审人"这个人真的能做出来"的信心？
- **关键句强化**：每个section的首句和末句是否有力？是否能让快速浏览的评审人抓住要点？

#### 2.3 逻辑连贯性
- 各研究内容之间的narrative thread是否清晰
- 立项依据→研究内容→技术路线→预期成果 是否一脉相承
- 段与段之间是否有合理的过渡和衔接
- 前后文是否存在矛盾之处

#### 2.4 术语一致性
- 同一概念是否全文使用同一术语（不要一会儿"深度学习"一会儿"深层学习"）
- 英文术语首次出现是否有中文对照
- 缩写是否首次出现时有全称

#### 2.5 数据准确性
- 引用的统计数据/数字前后是否一致
- 百分比、金额、年份等是否有明显错误
- 文献引用是否准确（作者、年份、期刊）

### Step 3: 格式合规检查

#### 3.1 篇幅检查
- 各章节字数是否在限制范围内（国自然正文一般不超过8000字）
- 参考文献数量是否适当
- 是否有章节过长或过短

#### 3.2 必备章节检查

权威源是项目 CLAUDE.md `## 章节规划` 表（由 `/fund-init` 按基金类型生成）。逐行对照 `sections/{NN}_{名}.md` 是否存在且有实质内容（非空、非占位注释），缺失或空壳均标为"需修改项"。**不要**在本 skill 里硬编码任何基金类型的章节清单——基金委模板分节与项目 sections 文件可能不同粒度，以 CLAUDE.md 表为准。

#### 3.3 图表格式
- 图片分辨率是否足够
- 图表标题是否规范（图在下、表在上）
- 技术路线图是否清晰易读
- 图表编号是否连续

#### 3.4 参考文献格式
- 格式是否统一（GB/T 7714 或其他指定格式）
- 是否有遗漏的引用
- 自引比例是否合理

#### 3.5 字体/排版要求（如有）
- 是否符合基金委模板要求
- 页边距、行距、字号是否正确

### Step 4: 跨章节一致性检查

#### 4.1 研究内容 ↔ 研究方案
- 研究内容中列出的每个子课题，在研究方案中是否都有对应的方法描述
- 研究方案中的方法，是否都服务于研究内容中的目标

#### 4.2 创新点 ↔ 立项依据
- 每个创新点是否都能在立项依据中找到对应的gap/不足
- 立项依据中指出的主要gap，是否都被创新点回应

#### 4.3 经费预算 ↔ 研究方案
- 需要购买的设备/软件，在研究方案中是否有体现
- 差旅费是否与调研/合作计划匹配
- 劳务费/专家咨询费是否与团队配置匹配

#### 4.4 年度计划 ↔ 研究内容
- 年度计划是否覆盖所有研究内容
- 时间分配是否合理（不要前松后紧或前紧后松）
- 预期成果是否与研究内容对应

### Step 5: 输出润色结果与合规报告

#### 润色结果（⚠️ 写入文件前必须通过用户确认门槛）

**硬门槛**（全局 CLAUDE.md 安全红线第一条："严禁未经确认就修改文件"）：

1. **自审报告**：把 Step 2 agent 产出的"修改摘要表"（原文 → 润色后 → 理由）逐章完整展示给用户，不写回任何 `sections/*.md` 文件
2. **逐段审批**：`AskUserQuestion` 给用户三个选项：
   - `(1) 全部接受本章修改` → 写回该章 .md 文件
   - `(2) 逐条审批` → 对每条 diff 单独询问 接受/拒绝/改写
   - `(3) 完全拒绝本章` → 跳过，不写回
3. **写回约束**：只有在用户选择 (1) 或逐条确认后，才用 Edit/Write 更新 `sections/{章节}.md`。选 (2) 的"改写"需 Agent 再跑一轮并再次进入本门槛。
4. **并行禁止**：多章节必须串行（一次只展示一章，用户拍板后再处理下一章）。

#### 合规报告
```
## 格式合规检查报告

### 通过项 ✓
- ...

### 需修改项 ✗
- [章节/位置] 问题描述 → 建议修改方式

### 跨章节一致性
- [一致/不一致] 具体说明
```

### Step 5.5: 灌入 main.tex（单轨模式落地）

所有章节 md 用户审批通过后，把 `sections/*.md` 的正文灌入 `main.tex` 对应 `\section{}` 下方（替换 fund-init Step 3.5 留下的 `% 本节正文待灌入自 sections/{NN}_{名}.md` 占位注释）。

**灌入规则**：
- md 中的 `# 章节标题` 和 frontmatter 注释（`<!-- 目标字数: ... -->` 等）**不灌入**，只灌入正文
- md 的 `##` 标题映射为 LaTeX `\subsection{}`；`###` 映射为 `\subsubsection{}`
- 列表、表格、公式、md 内嵌 LaTeX 命令（`\cite{}` / `\ref{}` / `$...$` 公式 / `\begin{table}...\end{table}`）统一用 `pandoc -f markdown+raw_tex -t latex sections/{NN}_{名}.md` 转 LaTeX 片段。`raw_tex` 扩展会原样保留所有 `\...` 命令和 `$...$` 公式，无需用户额外标注
- 章节间顺序严格按 CLAUDE.md `## 章节规划` 对应 main.tex `\section{}` 顺序

**写入前**：AskUserQuestion 展示灌入预览（每章 diff）供确认。**写入后**：跑 `latexmk -xelatex main.tex` 做编译验证，失败则记录到 build log 并提示用户排查。

### Step 6: 收尾

- **不**自动把阶段改为 `submitted`——`polishing → submitted` 不由本 skill 负责，应在用户真实投递时手动更新（或由未来的 `/fund-submit` skill 触发）。
- 向用户展示润色摘要 + 剩余改进建议，并提示："润色完成，main.tex 已灌入，可进入投递；投递后手动将 CLAUDE.md 的 `## 项目阶段` 改为 `submitted`。"

## 注意事项

- **润色不是重写**：保持申请人的原始思路和表达风格，只在规范性和说服力上提升
- **格式要求以最新版为准**：不同年份的基金申请格式可能有变化，以用户提供的模板为准
- **说服力 > 华丽**：基金申请书的核心是让评审人相信"这个问题重要、这个人能做、这个方案可行"，不是堆砌辞藻
- **关注评审人阅读体验**：评审人可能在短时间内阅读大量申请书，关键信息要一目了然
