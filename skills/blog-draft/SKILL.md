## 步骤 2：与用户对齐（2-3 个方案）

从素材中提炼出 **2-3 个不同的写作方案**，每个方案代表一种不同的切入角度和逻辑链。方案之间要有实质差异（不是换个标题），而是不同的论证路径、不同的情感基调、不同的读者收获。

设计方案时必须遵循 `_writing-craft.md` 中「深度」和「抓人眼球」的要求：
- 每个方案的开头设计必须制造认知冲突（反直觉断言 / 具体画面 / 灵魂拷问）
- 逻辑链至少穿透三层（现象 → 原因 → 结构性洞察）
- 标明哪些环节会用到个人经历做锚点

向用户展示：


## 步骤 2.3：个人锚点采集（关键步骤）

> **为什么需要这一步**：第一版文章最常见的问题是"缺少作者的血肉"——知识库素材+AI推演写出来的东西正确但缺少个人温度。用户的个人经历和感悟往往在看到方案后才会被激发，所以必须在开写前主动采集。

方案确认后，**主动向用户提问以下三个问题**（如果用户在初始请求或方案讨论中已经提供了个人经历，跳过已回答的问题，只补问未覆盖的部分）：

```
## 个人锚点采集

方案确认了，开写之前我需要你的"血肉"——

1. **这个主题让你想到自己哪段经历？**
   （不需要完整故事，几句话就行。比如某个场景、某个阶段、某次对话）

2. **你对这个主题最私人的感受是什么？**
   （不是"道理上我认为"，而是"我真实感受到的"。可以是矛盾的、说不清的）

3. **有没有哪句歌词/哪个观点是你反复想过的？**
   （帮我识别你最在意的着力点，写的时候会在这里加重笔墨）

你可以只回答一个，也可以三个都答。答得越具体，文章越有你的味道。
```

**用户回答后的处理：**
- 将用户提供的经历整理为具体的写作锚点（场景、时间、细节）
- 确定每个经历在文章逻辑链中的嵌入位置
- 如果用户经历涉及感情/恋爱，提醒用户这部分会泛化处理（参见 §3.2 禁忌）
- 如果用户没有相关经历可分享，标注"本篇无个人锚点，用知识库素材+假设场景"

**用户确认锚点安排后才继续。**

## 步骤 2.75：思想锻造（Deep Forging）

单次 LLM 调用产出的是"正确但可预测"的分析。真正有穿透力的洞察需要观点碰撞后的涌现——多个视角互相否定、互相补充，最终在张力交叉点产出新东西。

### 2.75.1 识别深度锚点

从步骤 2 确认的写作方案中，提取 **3-4 个"需要穿透三层"的核心论点**。选择标准：

- 方案中标注了"个人锚点"或"结构性洞察"的位置
- 容易被写成"正确但平庸"的观点——需要碰撞出意外深度的地方
- 与 Zylen 心智模型中的「内在张力」（_mental-model.md §六）产生共鸣的主题

每个锚点用一句话描述：「{主题} 的深层问题是 {问题}」

### 2.75.2 双 Agent 辩证碰撞

对每个深度锚点，**并行**启动两个 sub-agent：

**挑战者 Agent（Devil's Advocate）**
- 站在常识/主流立场，论证"为什么大多数人的看法是对的"
- 用真实的、有说服力的论据，**不是稻草人**
- 必须让 Zylen 读了会觉得"嗯，这话有道理，不好反驳"
- 产出：200-300 字的论证 + 1 句最强论据

**纵深者 Agent（Deep Diver）**
- 站在 Zylen 的立场（基于心智模型），把观点推到逻辑极限
- 连续追问三次"所以呢？这跟我有什么关系？为什么这很重要？"
- 直到撞到一个**意想不到的结论**——不是出发时能预见的
- 产出：200-300 字的纵深推演 + 1 句极限结论

**实现方式**：使用 Agent tool 并行启动两个 sub-agent（每个锚点两个调用，3-4 个锚点可分批并行）。如果 Agent tool 不可用，主 agent 可在内部依次模拟两个视角——先写完挑战者论证，再写纵深者推演，最后合成。

两个 Agent 的 prompt 必须包含：
- 当前锚点的一句话描述
- 相关的素材文件摘录（从步骤 1 提取的段落）
- 心智模型的对应信念/张力
- 写作风格要求（信息密度高、强观点短句收尾）

### 2.75.3 锻造合成

主 Agent 读两个 sub-agent 的产出，执行合成：

1. **找到张力交叉点**：双方都对但不完全对的那个点在哪里？
2. **写出三层递进**：现象（挑战者的"大多数人这么想"）→ 原因（纵深者的"但其实..."）→ 结构性洞察（合成的"真正的问题是..."）
3. **提炼可用素材**：金句、转折句、可以直接放进博客的段落

**每个锚点的锻造笔记格式：**

```
### 锚点 {N}：{主题}

**挑战者最强论据：** {1-2句}
**纵深者极限推论：** {1-2句}

**锻造洞察（三层递进）：**
第一层（现象）：{大多数人看到的}
第二层（原因）：{背后的机制}
第三层（结构性洞察）：{意想不到的结论}

**可用金句：** 「{一句话}」
```

### 2.75.4 向用户展示锻造结果

将 3-4 个锚点的锻造笔记展示给用户：

```
## 思想锻造结果

以下是 {N} 个深度锚点的碰撞产出，将嵌入博客的对应位置：

{锻造笔记1}
{锻造笔记2}
{锻造笔记3}

你觉得哪些洞察到位了？哪些还需要调整方向？
```

**用户确认/调整后才进入步骤 3 写作。** 如果用户对某个锚点不满意，可以：
- 指定新的碰撞方向（"这个点应该从 XX 角度切入"）
- 要求重新锻造（换一组 Agent 再跑一轮）
- 提供自己的洞察替换（用户自己的思考永远优先）

### 2.75.5 成本与节奏

- 3-4 个锚点 × 2 个 Agent = 6-8 次 sub-agent 调用（并行，耗时约等于单个 agent）
- 每个 sub-agent 只输出 200-300 字（论证一个观点，不是写文章）
- 合成步骤由主 Agent 完成，不额外调用
- 一篇 3000 字的博客中，3-4 处锻造洞察恰好对应每 700-1000 字一个深度爆点

## 步骤 3：写作

### 3.1 写作要求

- **字数**：3000-3500 字，不少于 3000 字
- **深度**：不是素材搬运，是基于素材的深度思考和重新组织。论证至少穿透三层（现象→原因→结构性洞察）；用个人经历做锚点；展示思考过程中的犹豫和转折。每篇文章至少 3 处使用步骤 2.75 的锻造洞察作为"深度爆点"——写到对应位置时，基于锻造笔记展开，不是从零思考
- **知识库深度融入**：Obsidian value 笔记中的洞察不是"引用"而是"论证支撑"——必须自然织入论述，让知识库素材成为文章的骨骼而非装饰。每篇至少深度使用 5 条以上知识库素材（金句、个人反思、价值观命题），不能只是通用哲学推演
- **歌词密度**（词间散记板块必须）：歌词解读类文章每篇至少 **5 处不同歌词段落**的独立引用+解读。歌词是论述骨架，不是装饰——每处引用后紧跟 2-3 段基于歌词的分析，不能引完就跳到别的话题
- **风格**：
  - 第一人称，个人化表达
  - 哲学思辨 + 生活化案例
  - 可以引用歌词、哲学家观点、个人经历
  - 段落不宜过长，保持阅读节奏
  - 有思想锐度，敢于表达不主流的观点
- **结构**：
  - 开头：必须制造认知冲突（反直觉断言 / 具体画面 / 灵魂拷问），不要用"在这个快节奏的时代"
  - 中间：层层递进，每个 section 有独立观点；每隔约 500 字要有一个钩子重新抓住读者（转折 / 新场景 / 金句）
  - 结尾：不要鸡汤式总结，留有余味或反转
- **节奏**：用长短句交错维持阅读节奏（参见 `_writing-craft.md` §三）；适当使用微幽默和多举例（§四）
- **语言**：中文为主，歌词/术语可保留原文（粤语、英文、日文）
- **格式**：markdown，使用 `##` 和 `###` 分节，`>` 引用歌词/名言，`**` 加粗关键概念

### 3.2 禁忌

- 不要写成 AI 味的"总分总"八股文
- 不要每段结尾都总结一遍
- 不要堆砌名人名言，引用要精准且有机融入
- 不要泛泛而谈，要有具体的、个人化的洞察
- **不暴露作者个人感情/恋爱经历**：工作经历、科研经历、性格自剖等个人锚点可以用，但涉及亲密关系的场景必须用第二人称假设场景（"你"视角）或泛化处理，不能写成作者自己的恋爱/婚姻/感情经历。即使文章主题是亲密关系，也不能暗示"我经历过这些"

## 步骤 4：生成配图

用 ChatAnywhere API 调用 Nano Banana 2（`gemini-3.1-flash-image-preview`）生成配图。

### 4.1 确定插图位置与尺寸

按文章段落结构，在每个 `##` 大节之间插入一张图。通常一篇 3000 字的文章需要 **1 张封面 + 4-5 张插图**，共 5-6 张。

| 用途 | 尺寸 | 说明 |
|:-----|:-----|:-----|
| 封面图 | 900×383px（2.35:1） | 微信公众号封面大图规范 |
| 正文配图 | 900×500px（9:5） | 微信文章正文最佳显示尺寸 |

> NB2 通过 prompt 指定尺寸比例，生成后用 `sips` 精确裁剪到目标尺寸。

### 4.2 绘图风格（文学漫画 · Literary Graphic Novel）

所有配图使用统一的「文学漫画」风格。

**固定风格签名（每个 prompt 必须包含）：**
```
sophisticated graphic novel illustration, confident ink linework with watercolor washes,
style reference: European BD meets Taniguchi Jiro — clean lines, atmospheric depth, literary sensibility.
No text.
```

**风格特征：**
- 线条干净自信，谷口治郎 + Moebius 的文学质感
- 水彩晕染做氛围，不是平涂
- 人物偏剪影或侧面，不做正面写实
- 画面留白多，呼吸感强
- 同一篇文章内所有图片配色统一

**配色随板块变化（不锁死颜色，锁风格）：**

| 板块 | prompt 配色关键词 | 适用场景 |
|:-----|:-----------------|:---------|
| **夕阳随笔** | warm amber, burnt sienna, soft indigo twilight | 人生哲学、存在主义、心态、人际关系、投资消费 |
| **词间散记** | muted teal, warm gold, soft paper texture tones | Eason、歌词解读 |
| **求索手记** | cool steel blue, warm grey, crisp morning light tones | 科研、AI/技术、方法论、注意力管理 |

> 未明确归属的主题默认使用「夕阳随笔」配色。

### 4.3 调用 API（chat/completions 接口）

NB2 通过 **chat/completions 接口**生成图片（不是 images/generations），返回 base64 编码图片。

```bash
source ~/.claude/scheduled/email-config.sh
cd /Users/zylen/Library/CloudStorage/Dropbox/04-Coding/academic-site
BASE="public/blog"

generate_nb2_image() {
  local output_path="$1"; local prompt="$2"
  curl -s -X POST "https://api.chatanywhere.tech/v1/chat/completions" \
    -H "Authorization: Bearer $CHATANYWHERE_API_KEY" \
    -H "Content-Type: application/json" \
    -d "{\"model\":\"gemini-3.1-flash-image-preview\",\"messages\":[{\"role\":\"user\",\"content\":\"Generate an image: $prompt\"}]}" \
    | python3 -c "
import sys, json, base64, re
d = json.load(sys.stdin)
content = d['choices'][0]['message']['content']
match = re.search(r'data:image/[^;]+;base64,([A-Za-z0-9+/=\n]+)', content)
if match:
    img_data = base64.b64decode(match.group(1))
    with open('$output_path', 'wb') as f:
        f.write(img_data)
    print(f'Saved: $output_path ({len(img_data)} bytes)')
else:
    print('ERROR: no image in response')
"
}

# **必须逐张串行生成**（NB2 走 chat 接口，每张约 60-90 秒；并行会触发 ChatAnywhere 限流导致请求挂起）
# 不要用 run_in_background 并行多批图片，会导致大部分请求超时失败
generate_nb2_image "$BASE/{slug}.png" "{cover_prompt}"
generate_nb2_image "$BASE/{slug}-01.png" "{prompt1}"
generate_nb2_image "$BASE/{slug}-02.png" "{prompt2}"
# ...
```

### 4.4 裁剪到目标尺寸

NB2 生成的图片尺寸不一定精确，用 `sips` 先等比缩放再裁剪（`sips -z` 是强制缩放会变形，不要用）：

```bash
# 封面：先按宽度等比缩放，再裁剪高度为 383
sips --resampleWidth 900 "$BASE/{slug}.png" --out "$BASE/{slug}.png"
sips --cropToHeightWidth 383 900 "$BASE/{slug}.png" --out "$BASE/{slug}.png"

# 正文配图：先按宽度等比缩放，再裁剪高度为 500
sips --resampleWidth 900 "$BASE/{slug}-01.png" --out "$BASE/{slug}-01.png"
sips --cropToHeightWidth 500 900 "$BASE/{slug}-01.png" --out "$BASE/{slug}-01.png"
```

### 4.5 归档素材

图片生成完成后，归档到 wechat-assets 项目（Dropbox 同步，永久保存）：

```bash
ASSETS="/Users/zylen/Library/CloudStorage/Dropbox/04-Coding/wechat-assets/blog/{slug}"
mkdir -p "$ASSETS"
cp "$BASE"/{slug}*.png "$ASSETS/"
cp "src/data/blog/{slug}.md" "$ASSETS/"
```

> **素材归档规范**：
> - 博客图片存两份：`public/blog/`（网站部署用）+ `wechat-assets/blog/{slug}/`（素材归档）
> - 博客文本存两份：`src/data/blog/{slug}.md`（网站部署用）+ `wechat-assets/blog/{slug}/{slug}.md`（素材归档）
> - 公众号头像等非博客素材存 `wechat-assets/avatars/`
> - 素材归档目录：`/Users/zylen/Library/CloudStorage/Dropbox/04-Coding/wechat-assets/`

### 4.6 插入文章

在文章 markdown 对应位置插入图片引用：

```markdown
![](/academic-site/blog/{slug}-01.png)
```

确保每张图片独占一个段落（前后各有一个空行），渲染器才能正确识别。

### 4.7 成本控制

- 模型：`gemini-3.1-flash-image-preview`（Nano Banana 2）via ChatAnywhere
- 接口：chat/completions（不是 images/generations）
- ChatAnywhere 定价：input 0.00125/1K tokens，output 0.3/1K tokens
- 预算：每篇文章 5-6 张 ≈ ¥2-4
- 思想锻造成本（Step 2.75）独立于配图成本，为纯文本推理调用

## 步骤 6：预览与迭代

> **核心原则**：第一版是"预览版"，不直接部署到线上。用户审阅全文后几乎一定会有反馈（补充个人经历、调整重点、修改措辞），迭代一轮后才是终版。

### 6.1 展示预览

向用户展示：
1. 文章标题 + 字数统计
2. 封面图（展示图片路径）
3. **完整正文**（不是前 500 字——用户需要看全文才能给出有效反馈）

询问：
- 哪里需要调整？
- 有没有想补充的个人经历或感受？
- 歌词/知识库素材的使用是否到位？

### 6.2 迭代修改

根据用户反馈修改文章。常见的反馈类型：
- 补充个人经历 → 在对应位置嵌入，保持叙事连贯
- 歌词交互不够 → 增加歌词引用+独立解读
- 某段论述太空泛 → 用知识库具体素材替换
- 语气/措辞调整 → 精修

**迭代可能需要 1-2 轮。用户说"OK"后才进入部署。**

### 6.3 部署

**用户确认终版后部署：**

```bash
cd /Users/zylen/Library/CloudStorage/Dropbox/04-Coding/academic-site
npm run build
npx gh-pages -d dist --dotfiles
```

> **注意**：必须加 `--dotfiles`，否则 `public/.nojekyll` 不会被推送，GitHub Jekyll 会吞掉 `_astro/` 目录导致 CSS 404。

## 边界条件

| 情况 | 处理 |
|:-----|:-----|
| Obsidian 素材不足 | 提示用户素材太少，建议先在 Obsidian 中积累再写 |
| 主题与已有博客重复 | 提示用户是扩写还是写新角度 |
| NB2 API 失败 | 重试 1 次；仍失败则回退 DALL-E 3（images/generations 接口）；再失败则跳过配图 |
| NB2 返回无图片 | 检查 response content 是否有 base64 数据，无则重试换 prompt 措辞 |
| `public/blog/` 目录不存在 | 自动创建 |
| 博客渲染器不支持图片 | 提醒用户需更新 `[slug].astro`，不自动修改 |
| `_mental-model.md` 不存在 | 跳过心智模型加载，提醒用户先运行 `/kb model` 生成 |

## 踩坑记录

| 坑 | 现象 | 教训 |
|:---|:-----|:-----|
| NB2 并行限流 | 3 批图片并行调用 ChatAnywhere，大部分请求挂起或超时 | **必须串行生成**，每张 60-90 秒，不要贪快并行 |
| 第一版直接部署 | 半成品文章被公开访问，用户反馈后需要重写 | 第一版是预览版，用户确认终版后才部署（见 Step 6） |
| 歌词只抓 chorus | 歌词解读文章引了两句歌词就开始自说自话 | 词间散记板块必须完整歌词+至少 5 处独立引用（见 Step 1.3） |
| 知识库素材浮于表面 | 文章读起来像"通用哲学散文"而非作者自己的思考 | 知识库素材必须是论证支撑而非装饰（见 Step 3.1） |
| 第一版缺个人经历 | 方案阶段只确认了角度，没采集用户的亲身故事 | 方案确认后必须跑「个人锚点采集」（见 Step 2.3） |
| frontmatter 缺 category | 博客列表页无法按板块筛选 | frontmatter 必须包含 `category` 字段（见 Step 5.1） |
